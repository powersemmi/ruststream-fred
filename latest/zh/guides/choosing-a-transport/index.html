    选择传输方式

    本指南比较服务读取的三种 Redis 结构：流、列表和 Pub/Sub 频道。

    示例是一个同时使用这三种结构的商店服务。 订单从流中读取并开具账单，缩略图从列表中读取并渲染，价格变动从频道到达。

    流：持久的日志​

    • 宏
    • 手写
    src/main.rs
    #[derive(Debug, PartialEq, Deserialize, Serialize, Outgoing)]
    #[outgoing(name = "orders")]
    struct Order {
        id: u64,
        amount_cents: u64,
    }

    #[derive(Debug, PartialEq, Deserialize, Serialize, Outgoing)]
    #[outgoing(name = "invoices")]
    struct Invoice {
        order_id: u64,
        amount_cents: u64,
    }

    #[subscriber(RedisStream::new("orders").group("billing"), reply)]
    async fn bill(order: &Order) -> Invoice {
        tracing::info!(order.id, "order billed");
        Invoice {
            order_id: order.id,
            amount_cents: order.amount_cents,
        }
    }
    src/main.rs
    #[derive(Debug, PartialEq, Deserialize, Serialize, JsonSchema)]
    #[schemars(crate = "ruststream::schemars")]
    struct Order {
        id: u64,
        amount_cents: u64,
    }

    #[derive(Debug, PartialEq, Deserialize, Serialize, JsonSchema)]
    #[schemars(crate = "ruststream::schemars")]
    struct Invoice {
        order_id: u64,
        amount_cents: u64,
    }

    named!(Order, "orders");
    named!(Invoice, "invoices");

    struct Bill;

    impl Handle<Order, Invoice> for Bill {
        fn handle(
            &self,
            order: &Order,
            _outs: &(),
            _ctx: &mut Context<'_>,
        ) -> impl Future<Output = Result<Invoice, HandlerOutcome>> {
            tracing::info!(order.id, "order billed");
            ready(Ok(Invoice {
                order_id: order.id,
                amount_cents: order.amount_cents,
            }))
        }
    }

    Redis 流保存每个条目，直到服务裁剪它。 RedisStream 通过消费者组读取流。 每个组都会收到每个条目一次，在组内由一个消费者处理它。 确认一个条目，就是对它执行 XACK。 消费者没有确认的条目留在组的待处理条目列表中，所以崩溃不会丢失任何东西。 用 seek 可以从较早的条目重新读取流。

    订单关系到钱，所以放在流上。 bill 用一张 Invoice 回复每个订单，回复写入流 invoices。

    列表：工作队列​

    • 手写
    src/main.rs
    #[derive(Debug, PartialEq, Deserialize, Serialize, Outgoing)]
    #[outgoing(name = "thumbnails")]
    struct Thumbnail {
        image: String,
    }

    #[derive(Debug, PartialEq, Deserialize, Serialize, Outgoing)]
    #[outgoing(name = "thumbnails.ready")]
    struct ThumbnailReady {
        image: String,
    }

    #[subscriber(RedisList::new("thumbnails").reliable(), reply)]
    async fn render(job: &Thumbnail) -> ThumbnailReady {
        tracing::info!(job.image, "thumbnail rendered");
        ThumbnailReady {
            image: job.image.clone(),
        }
    }
    src/main.rs
    #[derive(Debug, PartialEq, Deserialize, Serialize, JsonSchema)]

    struct Thumbnail {
        image: String,

    #[schemars(crate = "ruststream::schemars")]
    struct ThumbnailReady {
        image: String,
    }

    named!(Thumbnail, "thumbnails");
    named!(ThumbnailReady, "thumbnails.ready");

    struct Render;

    impl Handle<Thumbnail, ThumbnailReady> for Render {

            job: &Thumbnail,

            _ctx: &mut Context<'_>,

    }

    Redis 列表是一个队列：生产者推入一个条目，恰好一个消费者把它弹出。 RedisList::new 用 BRPOP 弹出条目，所以条目在处理器运行之前就离开了 Redis，处理器中的崩溃会丢失它。 reliable 则把条目移到处理中列表，等处理器确认之后才删除它。 列表没有组，也不能重放。

    渲染缩略图是交给一个工作者的工作，所以这些任务放在可靠列表上。 render 在频道 thumbnails.ready 上宣布每张完成的缩略图。

    Pub/Sub：广播​

    • 宏
    • 手写
    src/main.rs
    #[derive(Debug, PartialEq, Deserialize, Serialize, Outgoing)]
    #[outgoing(name = "prices")]
    struct PriceChange {
        sku: String,
        price_cents: u64,
    }

    #[subscriber(RedisPubSub::new("prices"))]
    async fn refresh_price(change: &PriceChange) -> HandlerOutcome {
        tracing::info!(change.sku, change.price_cents, "price cache refreshed");
        HandlerOutcome::ack()
    }
    src/main.rs
    #[derive(Debug, PartialEq, Deserialize, Serialize, JsonSchema)]
    #[schemars(crate = "ruststream::schemars")]
    struct PriceChange {
        sku: String,
        price_cents: u64,
    }

    named!(PriceChange, "prices");

    struct RefreshPrice;

    impl Handle<PriceChange> for RefreshPrice {
        fn handle(
            &self,
            change: &PriceChange,
            _outs: &(),
            _ctx: &mut Context<'_>,
        ) -> impl Future<Output = Result<(), HandlerOutcome>> {
            tracing::info!(change.sku, change.price_cents, "price cache refreshed");
            ready(Ok(()))
        }
    }

    Pub/Sub 消息到达发布那一刻已连接的每个订阅者。 Redis 不保存任何东西：未连接的订阅者永远看不到这条消息。 RedisPubSub 没有确认，所以处理器返回的结果不结算任何东西。

    价格变动只对此刻正在运行的实例有意义，它们会刷新自己的缓存，所以价格变动放在频道上。

    retry向流追加一份副本可靠列表：放回列表；简单列表：丢失丢失

    重放对组执行 seek无无

    确认各页完整说明每种结果，重试、延迟与死信展示延迟和上限在每种结构上如何工作。 流上的一批就是一次读取的 COUNT。 列表和频道一次投递一个条目，所以客户端收集同样大小的一批。

    一个名字只对应一种结构。 流和列表是特定类型的键，写入另一种类型会返回 WRONGTYPE 错误。 频道根本不是键：在频道名下执行 XADD 会写入一个流，频道的订阅者永远看不到它。

    一个服务，三种传输方式​

    • 宏
    • 手写
    src/main.rs
    #[ruststream::app]
    fn app() -> impl App {
        RustStream::new(AppInfo::new("shop", "0.1.0")).with_broker(
            RedisBroker::standalone("redis://localhost:6379"),
            |b| {
                b.include(bill).out_reply(stream::Publish);
                b.include(render).out_reply(pubsub::Publish::default());
                b.include(refresh_price);
            },
        )
    }
    src/main.rs
    fn app() -> impl App {
        RustStream::new(AppInfo::new("shop", "0.1.0")).with_broker(
            RedisBroker::standalone("redis://localhost:6379"),
            |b| {
                b.include(
                    subscriber(RedisStream::new("orders").group("billing"), Bill)
                        .reply()
                        .build(),
                )
                .out_reply(stream::Publish);
                b.include(
                    subscriber(RedisList::new("thumbnails").reliable(), Render)
                        .reply()
                        .build(),
                )
                .out_reply(pubsub::Publish::default());
                b.include(subscriber(RedisPubSub::new("prices"), RefreshPrice).build());
            },
        )
    }

    fn main() -> ExitCode {
        run_main(app)
    }

    只用一种传输方式的服务导入该传输方式的 prelude，例如 ruststream_fred::stream::prelude。 这个服务混用多种传输方式，所以导入 ruststream_fred::prelude。 在那里，每种传输方式的发布策略保留其模块名：stream::Publish 用 XADD 写入，pubsub::Publish 用 PUBLISH 写入。 回复类型指定回复发往哪里，挂载点上的策略指定它如何到达那里。

    三个处理器的形态相同。 把处理器换到另一种传输方式，改动的是它属性中的描述符和挂载点上的策略，而不是它的主体。

    示例文件中的测试向每种传输方式发布消息，并读取处理器发回的内容，全部在进程内完成。
