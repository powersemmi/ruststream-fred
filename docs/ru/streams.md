# Redis Streams {#redis-streams}

Поток Redis - это журнал: записи остаются в нём, пока поток не обрежут, а группа потребителей отдаёт
каждую запись одному из своих потребителей и помнит, что было подтверждено.

Сервис на потоках импортирует `ruststream_fred::stream::prelude::*`: дескриптор, типы перемотки
вместе с контекстами, в которых они лежат, и политику публикации этой формы под именем `Publish`.
`TransactionalPublish` - та же политика под транзакционным именем: издатель потока и без того
буферизует на дескрипторе.

Файл обработчика импортирует вместо этого `ruststream::prelude::*` и называет только ту
совместимость, которая нужна внедрённому издателю (`Out<impl Publisher>`,
`Out<impl TransactionalPublisher>`), поэтому перенос обработчика между формами меняет дескриптор, а
не обработчик.

Обработчик `#[subscriber("key")]` читает поток под этим ключом. Любое чтение идёт через группу
потребителей, поэтому форме с голой строкой нужна группа по умолчанию на весь брокер
(`.default_group`):

```rust
--8<-- "crates/ruststream-fred/examples/fred_streams.rs:handler"
```

Смонтируйте его на брокере:

```rust
--8<-- "crates/ruststream-fred/examples/fred_streams.rs:app"
```

Запись хранит полезную нагрузку в зарезервированном поле, а каждый заголовок - под префиксом `h:`,
поэтому `XADD` и `XREADGROUP` сохраняют и то и другое.

## Режимы чтения: с конца или перехват {#read-modes-fresh-tail-vs-reclaim}

Режим чтения выбирает конструктор, потому что эти два режима возвращают непересекающиеся наборы
записей:

- `RedisStream::new(key)` читает свежие записи с конца потока (`XREADGROUP >`). Это обычный рабочий
  подписчик.
- `RedisStream::reclaim(key, min_idle)` перехватывает записи, которые другой потребитель получил, но
  не подтвердил (`XAUTOCLAIM`, простой не меньше `min_idle`). Это восстановление после сбоя, и
  работает оно рядом с подписчиком `new` на той же группе («два обработчика на группу»).

У `min_idle` нет умолчания. Задайте его больше самого долгого времени работы обработчика, иначе
сообщение, которое исправный потребитель ещё обрабатывает, перехватывается и обрабатывается второй
раз.

Дескриптор можно написать в атрибуте `#[subscriber(..)]`. Рабочий подписчик, читающий с конца:

```rust
--8<-- "crates/ruststream-fred/examples/fred_reclaim.rs:worker"
```

Восстанавливающий обработчик на той же группе, перехватывающий записи, простоявшие больше 30 секунд:

```rust
--8<-- "crates/ruststream-fred/examples/fred_reclaim.rs:reclaim"
```

## Пакеты {#batches}

Параметр-срез делает обработчик пакетным, а размер пакета называет точка монтирования:

```rust
--8<-- "crates/ruststream-fred/examples/fred_seek.rs:batch-mount"
```

`batch(n)` обязателен на пакетном обработчике и отвергается на обработчике одного сообщения. На
потоке он становится значением `COUNT` у того `XREADGROUP` (или `XAUTOCLAIM`), который забирает
пакет: сервер присылает не больше этого числа записей, а обработчик видит ровно то, что вернуло одно
чтение.

Собственные настройки чтения Redis идут по цепочке после размера, из `RedisSubscribeExt` в прелюдиях
форм. `block(..)` задаёт, сколько одно чтение ждёт записей, и названное там значение перекрывает
значение дескриптора.

Списки и Pub/Sub отдают по одной записи за раз, поэтому их подписчики собирают пакеты на стороне
клиента и соблюдают тот же размер.

## Собственные поля доставки {#native-delivery-fields}

У Redis есть метаданные, которых нет в полезной нагрузке, и обработчик читает их по ключу из своего
типизированного контекста. Обработчик называет `StreamContext` типом своего контекста или
привязывает один ключ параметром `Ctx<K>`; тело пакетного обработчика называет `StreamBatchContext`.
Ключ, которого у этого транспорта нет, не компилируется.

| Ключ | Значение | Где |
| --- | --- | --- |
| `keys::EntryId` | `EntryId`, разобранный идентификатор `<milliseconds>-<sequence>`, под которым прочитана эта доставка | доставка |
| `keys::Position` | `RedisGroupPosition`, курсор, который доставит эту запись повторно | доставка |
| `keys::ConsumerGroup` | группа, через которую читает подписка | доставка и пакет |
| `keys::SeekHandle` | `RedisGroupSeeker`, ручка перемотки группы | доставка и пакет |

Пакет охватывает много доставок, поэтому `StreamBatchContext` держит только то, что принадлежит
подписке. Идентификатор записи и позиция принадлежат одной доставке и читаются с собственных
элементов пакета; запрос такого ключа на контексте пакета не компилируется.

Путь перехвата сообщает число доставок и время простоя заголовками `DELIVERY_COUNT_HEADER` и
`IDLE_MS_HEADER`, которые любой транспорт читает одинаково. У Pub/Sub свой `PubSubContext`
(совпавший канал и признак того, что доставка пришла по шаблону); список не передаёт ничего, кроме
полезной нагрузки и заголовков, поэтому его контекст остаётся `()`.

## Перемотка группы {#repositioning-a-group}

Группу можно отмотать назад по истории или вперёд, мимо записей, которые ей надо пропустить.
`StreamStart` выбирает, откуда группа начинает читать при создании; перемотка уже существующей
группы - это совместимость `Seekable`, которую потоки реализуют.

**Перемотка действует на всю группу.** Redis держит один курсор на группу потребителей, поэтому
перемотка сдвигает каждого потребителя этой группы, а не только ту подписку, которая её попросила.
Эта область записана в именах типов: `RedisGroupPosition` и `RedisGroupSeeker`.

Три позиции, по конструктору на каждую:

| Конструктор | Откуда группа продолжает |
| --- | --- |
| `RedisGroupPosition::beginning()` | самая старая запись, которая ещё хранится в потоке |
| `RedisGroupPosition::end()` | конец потока: только записи, добавленные позже |
| `RedisGroupPosition::after(id)` | запись, следующая за `id` (курсор исключающий, как у `XGROUP SETID`) |

Клауза `start_at(..)` перематывает подписку перед первой доставкой, на каждом старте:

```rust
--8<-- "crates/ruststream-fred/examples/fred_seek.rs:start-at"
```

Пока сервис работает, обработчик перематывает группу через ручку в собственном контексте:
`StreamContext` держит ручку перемотки группы под ключом `keys::SeekHandle`, который привязывают
параметром `Ctx`.

```rust
--8<-- "crates/ruststream-fred/examples/fred_seek.rs:seek-param"
```

Доставка сообщает свою позицию (`Positioned::position`, то же значение лежит под ключом
`keys::Position`). Перемотка на эту позицию доставляет сообщение заново, а за ним записи после него:
курсор исключающий, поэтому идентификатор уменьшается автоматически.

Тело пакетного обработчика перематывает ту же группу. Ручка перемотки принадлежит подписке, поэтому
она лежит на `StreamBatchContext` под тем же ключом, а запись, на которую реагирует пакет, берётся
из собственных элементов пакета:

```rust
--8<-- "crates/ruststream-fred/examples/fred_seek.rs:batch"
```

Чего перемотка не трогает:

- **список неподтверждённых записей.** Записи, уже отданные и не подтверждённые, остаются
  неподтверждёнными, куда бы ни сдвинулся курсор, и достижимы через путь перехвата.
- **запланированные отложенные повторы.** Копии, которые уже лежат в очереди задержки на ZSET,
  хранятся там под своим сроком, поэтому по наступлении срока они добавляются в поток независимо от
  того, откуда читает группа.
- **счётчики доставок.** Проигранная заново запись доставляется ещё раз, поэтому её собственный
  счётчик доставок Redis растёт; подписка перехвата с `max_deliveries` из-за этого засчитывает
  повторные проигрывания в предел, а заголовок фреймворка со счётчиком повторов сдвигается только на
  настоящем `nack`.

Курсор меняется, как только перемотка вернула управление; подписка, заблокированная в `XREADGROUP`,
видит это на следующем чтении, в пределах одного интервала `block`. Записи, выбранные старым
курсором, отбрасываются, а не доставляются.

## Подтверждение {#acknowledgement}

Доставка завершается по модели повторной публикации:

- `ack` -> `XACK` (убрать из списка неподтверждённых).
- `nack(requeue = true)` -> дописать копию в тот же поток, затем `XACK` оригинала. Копию
  обрабатывает обычный потребитель `new`. Это at-least-once: сбой между этими двумя командами
  оставляет дубль.
- `nack(requeue = false)` -> `XACK`, чтобы отбросить.

## Отложенная повторная доставка {#delayed-retry}

`HandlerOutcome::retry_after(delay)` просит отложенную повторную доставку, чтобы переждать временную
ошибку. У Redis Streams нет задержки на сообщение, поэтому подписка получает её одним из двух
способов.

Способ рантайма - копия сообщения, которую он публикует обратно в поток, когда задержка вышла:

```rust
--8<-- "crates/ruststream-fred/examples/fred_delayed_retry.rs:deferred"
```

Копия уходит через издателя, которого вы называете в точке монтирования шагом `out_retry`. Без него
задержка отбрасывается, а сообщение сразу возвращается в очередь. Копия работает по схеме
at-most-once на всём окне задержки: сбой до срабатывания таймера теряет её. Позиция - обычный слот
`Out`, поэтому `.transform(..)` после неё работает на копии, а заголовок со счётчиком повторов у
копии на единицу больше, чем у оригинала.

Очередь задержки на ZSET - долговечный способ: запланированная запись лежит в Redis, поэтому
повторная доставка переживает перезапуск. По умолчанию она выключена, и ключ ZSET называете вы:

```rust
--8<-- "crates/ruststream-fred/examples/fred_delayed_retry.rs:handler"
```

Отложенная доставка попадает в этот ZSET командой `ZADD` под свой срок, и заголовок со счётчиком
повторов при этом растёт на единицу, а оригинал подтверждается `XACK`. Подписка просматривает ZSET по
ходу чтения и командой `XADD` возвращает в поток записи, срок которых наступил, ничего в них не
меняя. Просмотр происходит один раз за чтение, поэтому гранулярность задаёт интервал `block`, а за
один проход возвращается не больше 128 записей. TTL на ключе ZSET убирает
брошенную очередь и должен быть больше самой долгой запланированной задержки, иначе записи пропадут
раньше, чем сработают. Вес записи - это миллисекунды эпохи по системным часам, поэтому держите часы
синхронными (NTP).

Обе подписки монтируются рядом, и издателя называет только та, у которой очереди нет:

```rust
--8<-- "crates/ruststream-fred/examples/fred_delayed_retry.rs:app"
```

## Ключи партиционирования {#partition-keys}

`workers(n, by_key)` запускает подписку на нескольких воркерах и сохраняет порядок внутри ключа:
доставки с одним ключом партиционирования попадают в одну партицию. `partition_key` - это шаг
публикации, поэтому он задаёт ключ одному сообщению:

<!-- inline-rust: two-publish fragment isolating the step; the compiled call sites are the crate's `partition_key` doctests, which need a connected broker and so cannot double as a snippet source here -->
```rust
use ruststream_fred::stream::prelude::*;
use serde::Serialize;

#[derive(Serialize, Outgoing)]
#[outgoing(name = "orders")]
struct Order {
    id: u64,
}

publisher.message(&Order { id: 7 }).partition_key("tenant-a").publish().await?;
publisher.message(&Order { id: 8 }).partition_key("tenant-a").publish().await?;
```

Шаг стоит в любом месте после сообщения и не занимает собственной позиции, поэтому он сочетается с
объявленным контрактом заголовков:

<!-- inline-rust: isolates the contract-plus-key chain; the compiled form is the `partition_key_step_composes_with_a_header_contract` test, whose broker setup would bury the four lines that matter -->
```rust
#[derive(Serialize, Outgoing)]
#[outgoing(name = "orders.keyed", headers = OrderMeta)]
struct KeyedOrder {
    id: u64,
}

#[derive(Serialize)]
struct OrderMeta {
    region: String,
}

publisher
    .message(&KeyedOrder { id: 7 })
    .with_headers(&OrderMeta { region: "eu".into() })
    .partition_key("tenant-a")
    .publish()
    .await?;
```

Собственные публикации обработчик ключует так же. Шаг принадлежит этому брокеру, поэтому такое тело
импортирует прелюдию этого крейта и называет тип настроек в ограничении слота:

<!-- inline-rust: the signature is the subject here; the compiled form is the `the_step_sets_the_key_the_delivery_reports` test, whose mount and assertions would bury it -->
```rust
use ruststream_fred::stream::prelude::*;

#[derive(OutSlot)]
#[publishes(Order)]
struct Ledger;

#[subscriber(RedisStream::new("orders.in").group("workers"))]
async fn forward(
    order: &Order,
    Out(ledger): Out<impl Publisher<Options = RedisPublishOptions>, Ledger>,
) -> HandlerOutcome {
    if ledger
        .message(order)
        .to("orders.keyed")
        .partition_key("tenant-a")
        .publish()
        .await
        .is_err()
    {
        return HandlerOutcome::retry();
    }
    HandlerOutcome::ack()
}
```

Своего понятия партиций у Redis нет, поэтому издатель пишет итоговый ключ в заголовок
`redis-partition-key`, и оттуда его читает принимающая сторона. Запись этого заголовка в точке
вызова - это форма, которая переносится между брокерами; шаг перекрывает её для своего сообщения, а
публикация без шага заголовки не трогает. Имя заголовка доступно публично как
`PARTITION_KEY_HEADER`, и шаг принимают все три транспорта.

## Совместимости {#capabilities}

Необязательные трейты-совместимости фреймворка и то, что из них реализует этот брокер. В примечаниях
сказано, где Списки и Pub/Sub отличаются от Streams.

| Совместимость | Нативно | Примечания |
| --- | --- | --- |
| `Subscribe` | да | Подписывается на ключ потока через группу потребителей (форме с голой строкой нужен `default_group`). Списки и Pub/Sub подписываются через свои дескрипторы. |
| `BatchSubscriber` | да, на всех трёх | На Streams нативно: `batch(n)` из точки монтирования становится значением `COUNT` у того `XREADGROUP` / `XAUTOCLAIM`, который забирает пакет, а сам пакет - это одно непустое чтение, и пустым он не бывает. Списки и Pub/Sub отдают по одной записи за раз, поэтому их подписчики собирают пакеты на стороне клиента и соблюдают тот же размер. См. [Пакеты](#batches). |
| `TransactionalPublisher` | да (Streams, standalone и sentinel) | Издатель потока буферизует на дескрипторе и фиксирует буфер одним блоком `MULTI` / `EXEC`. Издатель на кластере её отвергает, потому что блок `MULTI` не может охватить разные хеш-слоты. У издателей списка и Pub/Sub транзакции нет. См. [Транзакции](transactions.md). |
| `OwnedTransactions` | да (Streams, standalone и sentinel) | `publisher.transaction()` возвращает значение, владеющее буфером, поэтому на одном дескрипторе их может быть открыто сколько угодно; кластер отвергается по той же причине. |
| `RequestReply` | нет | В Redis нет примитива запрос-ответ: при передаче нигде не хранится адрес ответа и ничто не связывает ответ с запросом. |
| `Partitioned` | да | Все три транспорта читают ключ из заголовка `redis-partition-key` для партиций `workers(n, by_key)` в рантайме. Отправитель задаёт его шагом [`partition_key`](#partition-keys). |
| `Seekable` + `Positioned` | да (Streams) | Курсор группы двигает `XGROUP SETID`, а доставка сообщает позицию, которая доставит её повторно. Обработчики достают ручку перемотки по ключу контекста `keys::SeekHandle`; см. [Перемотка группы](#repositioning-a-group). Список разрушается при чтении, а Pub/Sub не хранит историю, поэтому у них этой совместимости нет. |
| `DescribeServer` | да | Сообщает хост и порт, на которые подключается клиент (первый seed-узел на кластере и sentinel). Учётные данные из URL, номер базы и параметры запроса в сгенерированный документ не попадают. Брокер, собранный через `RedisBroker::from_pool`, не сообщает хоста вовсе: адрес лежит в конфигурации самого пула. |
