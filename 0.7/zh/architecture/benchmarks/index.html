    基准测试

    ruststream-fred 在每条消息上的开销：与裸 fred 客户端对照的吞吐量，以及它自身代码的指令数和内存分配次数。

    与裸客户端对照​

    第一张图在真实的 Redis 服务器上把每个场景用三种方式运行。裸客户端 是在 fred 上手写的循环。Broker crate 是在本 crate 上写的同一个循环：Broker、订阅、投递流和 ack，上面没有运行时。RustStream 是用户写的服务：应用里的一个 #[subscriber] 处理器。第一项差值是本 crate 比它所封装的客户端多付出的开销，第二项是运行时在其上增加的开销。

    每个循环画成一条横条，从最佳一轮延伸到最慢的一轮，圆点标出最佳一轮，缺口标出中位一轮。坐标轴的零点是裸客户端的最佳一轮，圆点在零点右侧表示更慢。空心圆点表示该循环与裸客户端的差异小于各轮的波动范围。图表下方的表格列出最佳一轮，括号里是中位一轮。

    测量的形式有三种，每种传输方式一种：通过消费者组读取并确认每个条目的流、可靠列表，以及一个 Pub/Sub 频道。每种形式都分别在单机服务器、集群和 Sentinel 之后的主节点上运行。在集群上，Pub/Sub 一行使用分片形式，即 SSUBSCRIBE 和 SPUBLISH，集群上用的正是这种形式。

    代码的开销​

    第二张图统计一条消息在服务线程上的开销：稳态下 callgrind 测得的指令数和 DHAT 测得的内存分配次数。每个场景都是一个基于 RedisBroker 的服务，连接测试环境的单机服务器。服务运行在单线程运行时上，fred 也在同一线程上驱动它的连接，因此计数包括运行时、本 crate，以及 fred 编写命令和解析应答的工作。服务器是另一个进程，不计入。冷启动 是连接连接池、创建组、打开订阅并取得第一次投递一次性付出的开销。

    流场景用 XREADGROUP 读取消费者组，用 XACK 结算，用 XADD 应答。可靠列表用 BLMOVE 认领每个条目，用 LREM 结算它。Pub/Sub 场景读取一个频道或一个模式，不结算任何东西。.pipeline() 场景把一次读取的结算一起发送，它的处理器每次投递排入一条 INCR；.pipeline().atomic() 把每次投递的段包进 MULTI 和 EXEC，窗口一页用图说明了这一点。
