    Retries, delays and dead letters

    This guide retries a message now or later, caps the attempts and moves what keeps failing to a dead-letter stream.

    Redis has no per-message delay, no dead-letter structure, and a delivery count only inside a stream's consumer group. The framework supplies the rest: the mount site declares the cap and the destination, and the subscription chooses how a delay is kept.

    The example is a refunds service that sends refunds through a card processor.

    The subscriber​

    The processor refuses a refund in three ways, and each needs a different outcome. Busy means its rate limit is used up: a retry right now would be refused again, so retry_after waits 30 seconds. Unavailable means it did not answer: retry tries again at once. Declined means the card account is closed, and another try gets the same answer, so the refund is dropped.

    src/main.rs
    /// How long a busy processor asks its callers to wait.
    const BACKOFF: Duration = Duration::from_secs(30);

    #[derive(Debug, PartialEq, Serialize, Deserialize, Outgoing)]
    struct Refund {
        id: u64,
        card: String,
        amount_cents: u64,
    }

    #[subscriber(
        RedisStream::new("refunds")
            .group("refunds")
            .delayed_retry(DelayedRetry::DurableZset {
                key: "refunds.delayed".to_owned(),
                ttl: None,
            })
    )]
    async fn process_refund(
        refund: &Refund,
        State(processor): State<Arc<Processor>>,
    ) -> HandlerOutcome {
        settle(&processor, refund).await
    }

    async fn settle(processor: &Processor, refund: &Refund) -> HandlerOutcome {
        match processor.refund(refund).await {
            Ok(()) => HandlerOutcome::ack(),
            // Past the rate limit: a delivery right now would be refused again.
            Err(Refusal::Busy) => HandlerOutcome::retry_after(BACKOFF),
            // No answer: try again at once, up to the attempt cap.
            Err(Refusal::Unavailable) => HandlerOutcome::retry(),
            Err(Refusal::Declined) => {
                tracing::warn!(refund.id, "card declined, refund dropped");
                HandlerOutcome::drop()
            }
        }
    }
    src/main.rs
    /// How long a busy processor asks its callers to wait.
    const BACKOFF: Duration = Duration::from_secs(30);

    #[derive(Debug, PartialEq, Serialize, Deserialize, JsonSchema)]
    #[schemars(crate = "ruststream::schemars")]
    struct Refund {
        id: u64,
        card: String,
        amount_cents: u64,
    }

    impl OutgoingDestination for Refund {
        type Form = CallerName;
    }

    impl MessageHeaders for Refund {
        type Contract = NoHeaders;
    }

    struct ProcessRefund;

    impl Handle<Refund, (), (), (), Clients> for ProcessRefund {
        async fn handle(
            &self,
            refund: &Refund,
            _outs: &(),
            ctx: &mut Context<'_, (), Clients>,
        ) -> Result<(), HandlerOutcome> {
            settle(&ctx.state().processor, refund).await
        }
    }

    async fn settle(processor: &Processor, refund: &Refund) -> Result<(), HandlerOutcome> {
        match processor.refund(refund).await {
            Ok(()) => Ok(()),
            // Past the rate limit: a delivery right now would be refused again.
            Err(Refusal::Busy) => Err(HandlerOutcome::retry_after(BACKOFF)),
            // No answer: try again at once, up to the attempt cap.
            Err(Refusal::Unavailable) => Err(HandlerOutcome::retry()),
            Err(Refusal::Declined) => {
                tracing::warn!(refund.id, "card declined, refund dropped");
                Err(HandlerOutcome::drop())
            }
        }
    }

    fn refunds() -> RedisStream {
        RedisStream::new("refunds")
            .group("refunds")
            .delayed_retry(DelayedRetry::DurableZset {
                key: "refunds.delayed".to_owned(),
                ttl: None,
            })
    }

    retry on a stream appends a copy of the entry to the stream and acknowledges the original. On the other structures it does what the structure allows:

    Subscriptionretry without a cap
    RedisStream::new, reclaima copy appended to the stream
    RedisStream::claimingthe entry stays pending and comes back after min_idle
    RedisList::reliablethe entry moves back to the list
    RedisList::new, RedisPubSubnothing: the message is gone

    Under a declared cap, retry becomes a copy on every subscription but a claiming one, so the count travels with the message; a claiming entry carries Redis's own count.

    Three ways to keep a delay​

    retry_after settles the delivery and asks for it again after the delay. A subscription keeps that delay in one of three ways.

    The framework's own way needs nothing on the descriptor. The runtime holds a copy and publishes it back to the stream key once the delay is up. The copy carries the retry-count header, RETRY_COUNT_HEADER, raised by one. It lives in the process, so a service that stops before the delay ends loses it.

    DelayedRetry::DurableZset keeps the delay in Redis, which is what process_refund does. A delayed delivery goes into the sorted set refunds.delayed under its due time, with the retry count raised, and the original is acknowledged. As the subscription reads, it moves every due entry back onto the stream under a new id. The delay survives a restart of the service. A sweep runs once per read, so a delay ends within one block interval of its due time, five seconds by default. The scores are wall-clock milliseconds, so the clocks of the service's hosts need to agree. A ttl expires an abandoned set and has to be longer than the longest delay, or entries are lost before they are due.

    A claiming subscription is the third way, and it needs no set.

    src/main.rs
    fn priority_refunds() -> RedisStream {
        RedisStream::claiming("refunds.priority", BACKOFF).group("refunds")
    }

    A retry leaves the entry in the group's pending list, and the subscription's own next read takes it back once it has been idle min_idle. Nothing is copied, and the entry keeps its id. The only wait this offers is min_idle, so a shorter delay rounds up to it and a longer one is cut down to it. process_priority_refund sets min_idle to the backoff for that reason. A claiming subscription that names a DurableZset keeps each delay as asked instead.

    The cap and the dead-letter stream​

    • Macros
    • Manual
    src/main.rs
    #[ruststream::app]
    fn app() -> impl App<State = Clients> {
        RustStream::new(AppInfo::new("refunds", "0.1.0"))
            .on_startup(async move |()| Ok::<_, Infallible>(Clients::default()))
            .with_broker(RedisBroker::standalone("redis://localhost:6379"), |b| {
                // Five deliveries of one refund, the first included; then the dead-letter stream.
                b.include(process_refund)
                    .max_attempts(nonzero!(5u32))
                    .dead_letter("refunds.dlq");
                b.include(process_priority_refund)
                    .max_attempts(nonzero!(5u32))
                    .dead_letter("refunds.dlq");
                b.include(review);
            })
    }
    src/main.rs
    fn app() -> impl App<State = Clients> {
        RustStream::new(AppInfo::new("refunds", "0.1.0"))
            .on_startup(async move |()| Ok::<_, Infallible>(Clients::default()))
            .with_broker(RedisBroker::standalone("redis://localhost:6379"), |b| {
                // Five deliveries of one refund, the first included; then the dead-letter stream.
                b.include(subscriber(refunds(), ProcessRefund).build())
                    .max_attempts(nonzero!(5u32))
                    .dead_letter("refunds.dlq");
                b.include(subscriber(priority_refunds(), ProcessRefund).build())
                    .max_attempts(nonzero!(5u32))
                    .dead_letter("refunds.dlq");
                b.include(
                    subscriber(
                        RedisStream::new("refunds.dlq").group("refunds-review"),
                        Review,
                    )
                    .build(),
                );
            })
    }

    fn main() -> ExitCode {
        run_main(app)
    }

    max_attempts counts every delivery of one refund, the first included. The fifth delivery is not retried: dead_letter publishes it to refunds.dlq, payload and headers as they arrived. The dead letter is written the way the refund came in, so a refund from a stream lands on the stream refunds.dlq. A cap without a destination rejects the delivery at the cap, and a destination without a cap takes every retry on the first one. A dropped refund settles and goes nowhere; refunds.dlq holds only the refunds that ran out of attempts.

    The cap reads one count, and where it comes from depends on the subscription. A claiming subscription reads the delivery count Redis keeps for the entry. That count includes the deliveries of a worker that stopped, so a refund that crashed a worker counts against the cap too. Every other subscription reads the retry-count header on the copies the runtime publishes, and the delay set raises it on every round as well.

    A seek that replays entries delivers them again, as new deliveries. Redis counts a replayed entry's deliveries from one again, so a claiming subscription caps it from the replay on; the retry-count header does not move.

    Reading the dead letters​

    src/main.rs
    #[subscriber(RedisStream::new("refunds.dlq").group("refunds-review"))]
    async fn review(refund: &Refund, ctx: &mut Context<'_>) -> HandlerOutcome {
        let retry_count = ctx.headers().get_str(RETRY_COUNT_HEADER).unwrap_or("0");
        tracing::error!(
            refund.id,
            retry_count,
            "refund needs a person to look at it"
        );
        HandlerOutcome::ack()
    }
    src/main.rs
    struct Review;

    impl Handle<Refund, (), (), (), Clients> for Review {
        fn handle(
            &self,
            refund: &Refund,
            _outs: &(),
            ctx: &mut Context<'_, (), Clients>,
        ) -> impl Future<Output = Result<(), HandlerOutcome>> {
            let retry_count = ctx.headers().get_str(RETRY_COUNT_HEADER).unwrap_or("0");
            tracing::error!(
                refund.id,
                retry_count,
                "refund needs a person to look at it"
            );
            ready(Ok(()))
        }
    }

    refunds.dlq is an ordinary stream, and review reads it through a group of its own. A refund that came through copies carries the retry-count header, 5 here. review logs the refund for a person to look at.

    Patterns name their retry destination​

    A copy goes to the address the subscription reports: the stream key, the list key or the channel. A Pub/Sub pattern reads every channel its glob matches and names no single channel. Its registration names where a copy goes with out_retry, as .out_retry(Publish::default()).to("events.retry"), and the service does not start without it.

    Testing the delays​

    The tests in the example file run the service in process on a paused clock. tb.advance(BACKOFF) lets the 30 seconds pass at once, for the delay set and for the claiming subscription alike. Testing a Redis service covers the harness.
