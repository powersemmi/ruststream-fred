# Взаимодействие с другими клиентами

Это руководство показывает, что сервис на RustStream читает и пишет в Redis, чтобы производители и потребители на других языках работали с его потоками, списками и каналами.

Пример - сервис заказов.
Магазин, написанный на другом языке, добавляет заказы в поток, а почтовый сервис на другом языке извлекает письма из списка.

Запись потока Redis - это набор полей.
Сервис на RustStream хранит тело сообщения в поле `_payload`, а каждый заголовок в поле с именем `h:` и именем заголовка после него.
Производитель на любом языке записывает заказ, который прочитает сервис, так:

```bash
redis-cli XADD orders '*' _payload '{"id":1,"email":"ann@example.com"}' h:trace-id 4bf92f35
```

Тело - это то, что декодирует кодек. С кодеком по умолчанию это JSON, поэтому производитель записывает заказ в JSON.
Поле заголовка необязательно. Запись с одним `_payload` приходит без заголовков.
Поля с другими именами пропускаются, поэтому производитель может добавлять свои.
Запись без `_payload` написала другая программа. Её поля становятся телом сообщения в виде одного объекта JSON.
Значение в кодировке UTF-8 записывается строкой, любое другое значение записывается массивом чисел. Поля `h:` остаются заголовками:

```bash
redis-cli XADD orders '*' id 1 email ann@example.com
# тело: {"email":"ann@example.com","id":"1"}
```

Потребитель на другом языке читает записи, которые пишет сервис, так же: `_payload` содержит тело, а поля `h:` содержат заголовки.

Запись списка и сообщение Pub/Sub - это одно значение, поэтому заголовки передаются в кадре вокруг тела.
Сообщение без заголовков записывается как одно тело.
По умолчанию кадр двоичный. Он начинается с заголовка-метки `ruststream-frame` с пустым значением:

| Байты | Значение |
| --- | --- |
| 4 | число заголовков плюс один для метки, `u32` в порядке big-endian |
| 4, `ruststream-frame`, 4 | метка: длина имени 16, имя и длина значения 0 |
| 4, затем имя | для каждого заголовка: длина имени и имя |
| 4, затем значение | длина значения и значение |
| остаток | тело |

Тело без заголовков может нести метку там, где её несёт кадр. Такое тело записывается в кадре, поэтому читается без изменений.

[Кодек](../components/subscriptions/framing.md) в политике публикации вместо этого пишет конверт в формате этого кодека.
С `JsonCodec` почтовый сервис извлекает объект JSON:

```bash
redis-cli RPOP emails
# {"headers":{},"payload":"{\"to\":\"ann@example.com\",\"subject\":\"Order 1 received\"}"}
```

`payload` - это тело, здесь письмо в виде текста JSON, поэтому почтовый сервис разбирает конверт, а затем его `payload`.
Тело или заголовок в корректном UTF-8 записывается строкой, а любые другие байты - массивом чисел.
В таком конверте значения читаются и в инструменте вроде RedisInsight.

## Чтение значения списка или сообщения канала

Подписка читает кадр, который пишет её издатель: [`RedisList::codec`](api:ruststream_fred::list::RedisList::codec) и [`RedisPubSub::codec`](api:ruststream_fred::pubsub::RedisPubSub::codec) задают кодек конверта, а без него подписка читает двоичный кадр.
Подписка с кодеком читает и двоичные кадры, которые остаются после перехода сервиса на кодек.
Конверт читается только в точном виде: объект с полями `headers` и `payload` и без других полей.

Любое другое значение, например простой JSON, который добавляет или публикует другой клиент, приходит как тело без заголовков, какими бы ни были его первые байты:

```bash
redis-cli LPUSH jobs '{"id":7}'
redis-cli PUBLISH prices '{"sku":"tea","cents":450}'
```

Поэтому производитель на другом языке пишет простые значения, а если ему нужны заголовки, пишет конверт JSON.

В двоичном кадре версии 0.7.1 и более ранних метки нет. Текущая подписка читает такой кадр как тело вместе с байтами кадра.
Поэтому все сервисы одного списка или канала обновляются вместе, а старые значения из списка сначала вычитываются.
Подписка более ранней версии читает новый кадр и видит метку как ещё один заголовок.

## Тестирование

Тест в файлах примера работает внутри процесса: заказ приходит в том виде, в каком его пишет магазин, а значение в `emails` побайтно совпадает с конвертом JSON.
Тест с сервером читает и то и другое вторым клиентом `fred`, как это сделала бы другая программа: самая новая запись `orders` хранит заказ в `_payload`, а самое новое значение `emails` - это конверт.
