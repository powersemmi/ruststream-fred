# Побочные эффекты вместе с подтверждением

Это руководство отправляет собственные записи обработчика в Redis вместе с подтверждением его доставки.

Пример - сервис заказов.
Он ставит позиции каждого заказа в очередь комплектации склада, отвечает пронумерованной квитанцией и проводит платежи по бухгалтерскому журналу.

Обработчик, который пишет в Redis, а затем подтверждает доставку, тратит два обмена с сервером.
Сбой между ними применяет запись без подтверждения, и запись потока доставляется снова.

`Ctx<keys::Pipeline>` даёт обработчику [раунд](../components/pipelining/index.md) доставки, [`RedisPipeline`](api:ruststream_fred::pipeline::RedisPipeline).
Его [методы команд](../components/pipelining/commands.md) совпадают с методами `fred`: `lpush`, `hincrby`, `xadd`, `publish`, `eval` и остальные.
Вызов ставит команду в очередь и сразу возвращает управление.
`Ok` означает, что команда поставлена в очередь, а не что Redis её выполнил.

Команды из очереди уходят после возврата из обработчика и только если он подтверждает доставку.
Сначала идут они, затем `XACK`, в одном конвейере.

| Исход | Команды из очереди | Завершение доставки |
| --- | --- | --- |
| `ack` | отправляются до завершения | `XACK` |
| `drop` | отбрасываются | `XACK` |
| `retry`, `retry_after` | отбрасываются | копия для переобработки, затем `XACK` |
| не завершена | отбрасываются | нет: запись остаётся неподтверждённой |

`accept` ставит в очередь по одной команде добавления на позицию.
Позиция без количества отбрасывает заказ, и вместе с ним отбрасываются команды, поставленные для предыдущих позиций.

## Чтение значения сразу

У команды из очереди нет ответа внутри обработчика.
Значение, которое обработчику нужно сразу, он получает через пул соединений брокера, который даёт [`Ctx<keys::FredPool>`](../components/context/fred-pool.md).
Так `accept` нумерует каждую квитанцию командой `INCR`.
Рядом с `keys::Pipeline` параметр `keys::FredPool` стоит в сигнатуре вторым.

`.pipeline()` в точке монтирования открывает окно, и команды обработчика можно поставить в очередь только на подписке, смонтированной с этим шагом.
Обработчик, который принимает `Ctx<keys::Pipeline>` и смонтирован без этого шага, не компилируется.

Без преобразования ответ публикуется сразу после возврата из обработчика, раньше раунда.
Преобразование [`InRound`](../components/pipelining/in-round.md) на ответе помещает его в раунд после команд, поэтому квитанция уходит только вместе с комплектацией.
Публикация через слот `Out` входит в раунд, когда обработчик [привязывает](../components/pipelining/bind.md) слот вызовом `pipeline.bind(out)`.

Окно собирает раунды всех доставок одного чтения.
Окно отправляется, когда завершены все доставки чтения, поэтому под нагрузкой весь полученный пакет уходит за один обмен с сервером.
При редком потоке сообщений окно отправляется сразу после возврата из последнего обработчика.
Об ошибке отправки сообщается один раз, с подпиской и числом команд и завершений в окне.
Записи, `XACK` которых не прошёл, остаются неподтверждёнными и доставляются снова.

Пакетный обработчик берёт раунд из своего контекста, `ctx.context(keys::Pipeline)`, и его команды уходят, только если подтверждена каждая запись пакета ([Отправка](../components/pipelining/flush.md)).

Конвейер - не транзакция: команда может выполниться, а `XACK` после неё вернуть ошибку.
[`.atomic()`](../components/pipelining/atomic.md) после `.pipeline()` заключает команды каждой доставки и её завершение в `MULTI` и `EXEC`.
Тогда запись в журнале, баланс и подтверждение платежа выполняются вместе или не выполняются вовсе.

В Redis нет отката.
Команда, которая возвращает ошибку внутри `EXEC`, например `HINCRBY` на ключе другого типа, оставляет остальные применёнными.

В [кластере](cluster.md) блок `MULTI` выполняется в одном хеш-слоте.
Поток называется `{payments}`, а ключи обработчика `{payments}:ledger` и `{payments}:balances`: хеш-тег в фигурных скобках помещает их все в слот потока.
В имени потока есть фигурные скобки, поэтому тип платежа не объявляет место назначения, а производитель задаёт поток при публикации.

## Скрипты Lua

`eval` и `evalsha` ставят скрипт Lua в очередь, как любую другую команду, и скрипт выполняется в раунде вместе с завершением доставки.
Скрипт выполняется на сервере атомарно, поэтому подходит для проверки и записи, которые нельзя разделять.
[Redis внутри процесса](../components/testing/index.md) не выполняет скрипты, поэтому тест обработчика, который ставит скрипт в очередь, работает с сервером.

## Тестирование

Тесты в файлах примера публикуют заказ, отброшенный заказ и платёж внутри процесса.
Они читают комплектацию, квитанцию и запись в журнале и проверяют, что отброшенный заказ не отправляет ничего из поставленного в очередь.
