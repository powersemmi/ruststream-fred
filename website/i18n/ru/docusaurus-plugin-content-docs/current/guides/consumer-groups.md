# Группы потребителей и восстановление после сбоя

Это руководство делит поток Redis между воркерами и между сервисами и возвращает в работу записи, которые не закончил остановившийся воркер.

Пример - платёжный сервис.
Платежи приходят в поток `payments`.
Группа бухгалтерского журнала проводит каждый платёж, а группа антифрода его проверяет.

Поток Redis читается через группу потребителей.
Группа хранит курсор в потоке, и каждая запись за курсором достаётся одному потребителю группы.
Каждая подписка - это один потребитель. Поэтому каждый работающий экземпляр сервиса добавляет потребителя в `ledger`, и экземпляры делят платежи между собой.
Потребитель получает сгенерированное имя: `ruststream-0`, `ruststream-1` и так далее в каждом процессе.
[`consumer`](api:ruststream_fred::stream::RedisStream::consumer) задаёт имя, например по имени хоста, чтобы `XINFO CONSUMERS` различал экземпляры.

Запись, выданная потребителю, попадает в список неподтверждённых записей группы.
Она покидает этот список, когда обработчик её подтверждает.
Если воркер останавливается раньше, из-за сбоя или развёртывания, запись остаётся неподтверждённой: Redis хранит её, и сам он не передаёт её другому потребителю.

[`RedisStream::claiming`](../components/streams/claiming.md) читает оба набора за один вызов: сначала записи, которые ждут подтверждения не меньше `min_idle`, затем новые.
Поэтому подписка, которая принимает новые платежи, перехватывает и платежи остановившегося воркера.
Ей нужен Redis 8.4 или новее. На более старом сервере сервис не запускается, а ошибка называет подписку и обе версии.

`retry` на этой подписке не добавляет копию.
Запись остаётся неподтверждённой под своим идентификатором, и следующее чтение перехватывает её, когда она простоит `min_idle`.
`post_payment` пользуется этим для счёта, который переносится: платёж ждёт в списке неподтверждённых записей и возвращается каждые 30 секунд.

У перехваченной записи есть заголовок [`DELIVERY_COUNT_HEADER`](../components/acknowledgement/counts.md) с числом доставок до этой. У новой записи он равен нулю.
[`IDLE_MS_HEADER`](api:ruststream_fred::IDLE_MS_HEADER) хранит, сколько запись простояла.
Как ограничить число доставок по этому счётчику, показывает руководство [Переобработка, задержки и dead-letter](retries.md).

## Выбор min_idle

У `min_idle` нет значения по умолчанию.
Запись, которая простояла столько, считается брошенной, поэтому задайте значение больше самого долгого времени работы обработчика.
Меньшее значение отбирает запись у воркера, который ещё её обрабатывает, и платёж проводится дважды.
Большее значение на столько же задерживает восстановление после сбоя.

У каждой группы свой курсор и свой список неподтверждённых записей, поэтому каждая группа читает каждую запись.
Группа антифрода получает каждый платёж, который получает группа журнала, и ни одна не замедляет другую.
На практике у каждого сервиса, который читает поток, своя группа.

Сервис создаёт группу при запуске, если её ещё нет.
[`start_id`](../components/streams/stream-start.md) задаёт, откуда начинает новая группа. [`StreamStart::New`](api:ruststream_fred::stream::StreamStart::New), значение по умолчанию, читает только записи, добавленные после создания группы, а [`StreamStart::Beginning`](api:ruststream_fred::stream::StreamStart::Beginning) читает все записи, которые поток ещё хранит.
Группу антифрода добавили позже группы журнала, поэтому она начинает с начала и проверяет платежи, которые уже лежат в потоке.
Существующая группа сохраняет свой курсор, и `start_id` его не сдвигает. Его сдвигает [start_at](../components/positions/start-at.md).

## Порядок по счёту

`workers(8, by_key)` запускает `post_payment` в восьми партициях.
Платежи с одинаковым ключом партиционирования попадают в одну партицию и обрабатываются друг за другом, поэтому платежи одного счёта проводятся в том порядке, в каком их добавили.
В Redis нет разделов, поэтому ключ передаётся в заголовке [`PARTITION_KEY_HEADER`](api:ruststream_fred::PARTITION_KEY_HEADER).
Производитель задаёт его шагом [`partition_key`](../components/publishing/partition-key.md) своей публикации.
Платёж без ключа попадает в любую партицию.
Порядок соблюдается внутри одного потребителя. Два экземпляра сервиса проводят каждый свою долю платежей.

У более старого сервера нет чтения с перехватом, поэтому восстановление - это вторая подписка на ту же группу.
[`RedisStream::new`](../components/streams/index.md) читает новые записи.
[`RedisStream::reclaim`](../components/streams/reclaim.md) командой `XAUTOCLAIM` читает только записи, которые ждут подтверждения не меньше `min_idle`, и так перехватывает то, что держал остановившийся воркер.
Перехваченная доставка учитывает себя в `DELIVERY_COUNT_HEADER`, поэтому первое восстановление сообщает как минимум 1.

На подписке `new` вызов `retry` добавляет копию записи в поток и подтверждает оригинал.
Копия возвращается сразу, после записей, добавленных за это время.
Для ожидания вроде переноса счёта выше там нужен `retry_after`, о котором рассказывает руководство [Переобработка, задержки и dead-letter](retries.md).

## Тестирование восстановления

Тесты в файле примера запускают сервис внутри процесса с остановленными часами.
Один из них публикует платёж по счёту, который переносится, сдвигает часы на `min_idle` через `tb.advance` и видит, что журнал получает платёж второй раз, а копии в потоке нет.
Обвязку описывает руководство [Тестирование сервиса на Redis](testing.md).
