# Redis Cluster

Это руководство запускает сервис на Redis Cluster и даёт ключам имена так, чтобы ключи одной команды находились в одном хеш-слоте.

Пример - серверная часть магазина.
Она выполняет задания из очереди заданий, выставляет счета по заказам из потока и слушает события в шардированном канале.

[`RedisBroker::cluster`](../components/broker/cluster.md) принимает начальные узлы.
Достаточно одного доступного узла: клиент читает с него устройство кластера и подключается к каждому ведущему узлу.
Как и любой конструктор брокера, этот не выполняет ввода-вывода. Соединение открывается при запуске сервиса.

Обработчики одинаковы на одиночном сервере и в кластере.
Меняется то, как сервис называет свои ключи.

## Хеш-теги

Кластер распределяет ключи по 16384 хеш-слотам, и каждый ведущий узел владеет их диапазоном.
Команда, блок `MULTI` или скрипт, которые затрагивают несколько ключей, выполняются, только если все ключи находятся в одном слоте.
Слот определяет хеш-тег: если в ключе есть часть в фигурных скобках, хешируется только она.
`{jobs}` и `{jobs}.processing` находятся в одном слоте, как и `{orders}` и `{orders}:invoices`.

Имя в фигурных скобках не может быть постоянным местом назначения типа, потому что `#[outgoing(name = "..")]` читает фигурные скобки как шаблон имени.
Производитель задаёт такой ключ там, где публикует: `.message(&job).to("{jobs}")`.

[Надёжный список](../components/lists/reliable.md) переносит каждую запись в список обработки одной командой `LMOVE`, поэтому оба ключа должны находиться в одном слоте.
Список обработки называется как очередь с добавленным `.processing` и сохраняет хеш-тег очереди.
Надёжный список, два ключа которого попадают в разные слоты, не запускается, а ошибка называет хеш-тег, который нужно использовать.

Поток - это один ключ, поэтому подписка на поток работает под любым именем.
[Атомарное окно](pipelining.md#atomic-segments) помещает команды обработчика и `XACK` в один блок `MULTI`, и блок выполняется в слоте потока.
`invoice` пишет в `{orders}:invoices`, в слот потока `{orders}`.
Команда для ключа в другом слоте заставляет Redis отклонить весь блок: ничего не записывается, и запись потока остаётся неподтверждённой.

[Транзакция](transactions.md) издателя потока - тоже блок `MULTI`, и её места назначения не привязаны к одному слоту.
Поэтому кластер отклоняет оба вида транзакций: открытие любой из них возвращает ошибку.

Классический Pub/Sub в кластере отправляет каждое сообщение на каждый узел.
[`PubSubMode::Sharded`](../components/pubsub/pubsub-mode.md) отправляет его только на узел, которому принадлежит слот канала, командами `SPUBLISH` и `SSUBSCRIBE`, поэтому трафик масштабируется вместе с кластером.
Этому режиму нужен Redis 7 или новее.

Два режима не видят друг друга: шардированное сообщение никогда не доходит до классического подписчика, и наоборот.
Издатель канала использует режим подписки.
[Подписка по шаблону](../components/pubsub/pattern.md) бывает только классической.

## Тестирование сервиса на кластере

Тесты запускают промышленное приложение через `TestApp::start` с брокером кластера.
[Redis внутри процесса](../components/testing/index.md) ведёт себя как кластер: он отклоняет команду или блок, которые охватывают несколько хеш-слотов.
Поэтому тесты проверяют, что каждая форма работает с хеш-тегами сервиса, что надёжный список без тега не запускается и что блок на два слота ничего не фиксирует.
То же тело теста работает с настоящим кластером, когда `REDIS_CLUSTER_TEST_URL` называет его узел.

Переключение при отказе и перераспределение слотов бывают только на настоящем кластере. Что брокер делает в этих случаях, описывает [руководство по промышленной эксплуатации](production.md).
