# Выбор транспорта

Это руководство сравнивает три структуры Redis, которые читает сервис: поток, список и канал Pub/Sub.

Пример - сервис магазина, который работает со всеми тремя.
Счета по заказам выставляются из потока, миниатюры строятся из списка, а изменения цен приходят по каналу.

Поток Redis хранит каждую запись, пока сервис её не обрежет.
[`RedisStream`](../components/streams/index.md) читает поток через группу потребителей.
Каждая группа получает каждую запись один раз, а внутри группы её обрабатывает один потребитель.
Подтверждённая запись получает `XACK`.
Запись, которую потребитель не подтвердил, остаётся в списке неподтверждённых записей группы, поэтому сбой ничего не теряет.
Поток можно прочитать заново с более ранней записи через [перемотку](../components/positions/seek.md).

Заказы - это деньги, поэтому они идут через поток.
`bill` отвечает на каждый заказ счётом `Invoice`, который попадает в поток `invoices`.

Список Redis - это очередь: производитель добавляет запись, и ровно один потребитель её извлекает.
[`RedisList::new`](../components/lists/index.md) извлекает запись командой `BRPOP`. Запись покидает Redis до запуска обработчика, и сбой в обработчике её теряет.
[`reliable`](../components/lists/reliable.md) вместо этого переносит запись в список обработки и удаляет её только после подтверждения обработчиком.
У списка нет групп и нет повторного чтения.

Построение миниатюры - работа для одного воркера, поэтому задания идут через надёжный список.
`render` объявляет о каждой готовой миниатюре в канале `thumbnails.ready`.

Сообщение Pub/Sub получает каждый подписчик, подключённый в момент публикации.
Redis ничего не хранит: подписчик, который не подключён, сообщение не увидит.
У [`RedisPubSub`](../components/pubsub/index.md) нет подтверждения, поэтому исход, который возвращает обработчик, ничего не завершает.

Изменение цены важно только экземплярам, которые работают сейчас и обновляют свой кеш, поэтому оно идёт через канал.

## Сравнение

| | Поток | Список | Pub/Sub |
|---|---|---|---|
| Хранится, пока никто не читает | пока не обрезан | пока не извлечён | нет |
| Кто получает сообщение | один потребитель в каждой группе | один потребитель | каждый подключённый подписчик |
| `ack` | `XACK` | надёжный: `LREM` из списка обработки; простой: ничего | ничего |
| `retry` | копия, добавленная в поток | надёжный: обратно в список; простой: теряется | теряется |
| `retry_after` | копия после задержки | копия после задержки | копия после задержки |
| Пакет | одно чтение до `n` записей | собирает клиент | собирает клиент |
| Повторное чтение | перемотка группы | нет | нет |

Страницы о [подтверждении](../components/acknowledgement/index.md) описывают каждый исход полностью, а руководство [Переобработка, задержки и dead-letter](retries.md) показывает, как работают задержка и предел попыток на каждой структуре.
[Пакет](../components/subscriptions/batches.md) на потоке - это `COUNT` одного чтения.
Список и канал доставляют по одной записи, поэтому пакет того же размера собирает клиент.

Одно имя занимает одна структура.
Поток и список - это ключи определённого типа, и запись другого типа возвращает ошибку `WRONGTYPE`.
Канал вообще не ключ: `XADD` под именем канала создаёт поток, которого подписчики канала никогда не увидят.

Сервис на одном транспорте импортирует прелюдию этого транспорта, например `ruststream_fred::stream::prelude`.
Этот сервис сочетает транспорты, поэтому импортирует [`ruststream_fred::prelude`](../components/broker/prelude.md).
В ней политика публикации каждого транспорта сохраняет имя своего модуля: `stream::Publish` пишет командой `XADD`, `pubsub::Publish` командой `PUBLISH`.
Тип ответа задаёт, куда уходит ответ, а политика в точке монтирования задаёт, как он туда попадает.

Три обработчика устроены одинаково.
Чтобы перенести обработчик на другой транспорт, меняют дескриптор в его атрибуте и политику в его точке монтирования, а тело остаётся прежним.

Тесты в файле примера публикуют в каждый транспорт и читают то, что отправили в ответ обработчики, и всё это внутри процесса.
