# 数字

`ruststream-fred` 的基准测试数字测的是什么，以及不能从中得出哪些结论。

## 与裸客户端的对照 {/* #the-comparison-against-a-raw-client */}

同一行中的三个循环可以互相比较，因为它们在同一个进程中、交替地、对着同一台服务器运行。一行不能与另一个 Broker crate 公布的行比较：各种传输方式在每条消息上做的工作不同。

服务器运行在同一台机器上，使用宿主机网络，并关闭了持久化。没有网络延迟，也没有磁盘，同样的每条消息开销在时间中所占的比例，比面对跨网络的服务器时更大。应把该百分比读作已部署服务所付代价的上界。

`受 Broker 限制` 的行表示裸客户端在运行的大部分时间里都在等套接字。本 crate 和运行时的工作于是发生在这段等待之内，测出的差异接近零。这是开销的下界，而不是对它的测量。

Pub/Sub 一行是在一个从不等待消费者的发布者下测得的。订阅来不及取走的消息，Pub/Sub 会直接丢弃，因此这一行报告的是一个饱和的订阅每秒处理的投递数。

## 代码的开销 {/* #the-cost-of-the-code */}

指令计数包括运行时、本 crate 以及 `fred` 在服务线程上的工作。它包含框架自身的开销；核心库在它的[基准测试页面](https://powersemmi.github.io/ruststream/latest/zh/architecture/benchmarks/)上单独公布这部分开销。同样的计数在缓存未命中处要花更多时间，因此计数不等于时间。

每个数字都是稳态，即 1000 次投递的运行与 2000 次投递的运行之差。连接、创建组以及它们背后的首批内存分配属于冷启动，只付一次。

## 它们不意味着什么 {/* #what-they-do-not-mean */}

一行就是一个消费者读取一个键，消息体很小，服务器在回环接口上。它测量的是一次投递在本 crate 及其上的运行时内部的开销，而不是 Redis 能承载多少。

一次运行的计时窗口从第一次投递开始，到最后一次投递被取走时结束，三个循环都一样。因此在每个循环里，一次运行都有一次确认落在数字之外。

发布路径不在对照之中：三个循环共用一个发布者。代码图在同一测试环境上统计应答。

这些数字是一台机器在某一天的快照，构建信息记录在旁边。它们在一台只做这次运行的机器上手动重新测量：它们显示的差异小于共享机器的噪声。
